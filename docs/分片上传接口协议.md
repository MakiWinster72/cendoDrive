# 大文件分片上传接口协议

本文是任务 43 前后端分片上传对接契约。上传任务、分片状态和分片文件都按当前用户隔离；所有接口均需 `Authorization: Bearer <token>`。普通上传继续使用 `POST /api/files/upload`；文件大于 100 MiB 时前端改走本协议。

## 当前服务端实现与部署限制

- 任务元数据持久化到数据库，分片暂存于 `cendo.upload.root`（环境变量 `CENDO_UPLOAD_ROOT`，默认 `./storage/uploads`）；需保持目录持久化、可写。多实例需共享目录或采用会话亲和。
- 分片最大 5 MiB，最多 2048 片；每用户最多 20 个未完成任务。初始化时预留额度，普通上传、其他任务或复制不能挤占已预留容量。
- 任务默认有效 24 小时，可通过 `CENDO_UPLOAD_TTL_HOURS` 配置；定时清理过期元数据和暂存目录，过期任务不能继续上传。
- 未完成任务初始化和重复分片幂等；合并校验完整内容 MD5，成功后的重复合并返回原文件，不重复写入或占用容量。
- 补充错误：`INVALID_UPLOAD` / `INVALID_CHUNK`（400）、`HASH_MISMATCH`（400）、`QUOTA_EXCEEDED`（507）、`UPLOAD_EXPIRED`（410）、`TOO_MANY_UPLOADS`（429）。

## 约定

- 单片大小：5 MiB（5,242,880 字节）；最后一片可以小于该值。
- 分片序号从 `0` 开始。
- `fileHash` 使用文件完整内容的 MD5 小写十六进制串（32 字符），用于识别同一文件并恢复未完成任务，不作为安全凭证。
- 初始化以当前用户、`fileHash` 和 `parentId` 幂等；未完成的同一上传应返回原 `uploadId`。
- 已成功接收的同一分片重复提交应幂等返回成功，不得破坏已接收分片。
- 根目录时 `parentId` 为 `null`；`parentId` 在请求中使用十进制 ID 字符串。
- 成功的文件 DTO 沿用 `docs/文件管理接口文档.md` 中的 `FileResponse`，不额外包装 `data`。

## 初始化上传

`POST /api/upload/init`，`Content-Type: application/json`。

```json
{
  "fileName": "archive.zip",
  "fileSize": 12582912,
  "fileHash": "0123456789abcdef0123456789abcdef",
  "parentId": null,
  "chunkSize": 5242880,
  "totalChunks": 3
}
```

成功返回 `200 OK`：

```json
{
  "uploadId": "opaque-upload-id",
  "chunkSize": 5242880,
  "totalChunks": 3
}
```

同一用户对相同 `fileHash`、`parentId` 的未完成上传应返回可续传的任务 ID。

## 查询分片状态

`GET /api/upload/{uploadId}/status`。

成功返回 `200 OK`：

```json
{
  "uploadId": "opaque-upload-id",
  "totalChunks": 3,
  "uploadedChunks": [0, 2]
}
```

`uploadedChunks` 是服务端已持久接收的分片序号。前端只发送缺少的分片；任务及分片必须属于当前用户。

## 上传单个分片

`POST /api/upload/chunk`，`Content-Type: multipart/form-data`。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `uploadId` | string | 是 | 初始化返回的上传任务 ID |
| `chunkNumber` | integer | 是 | 从 0 开始的分片序号 |
| `totalChunks` | integer | 是 | 文件分片总数 |
| `fileHash` | string | 是 | 初始化时的文件 MD5 |
| `chunk` | binary | 是 | 当前分片内容 |

成功返回 `200 OK`：

```json
{
  "uploadId": "opaque-upload-id",
  "chunkNumber": 1,
  "received": true
}
```

重复提交已成功接收的分片应返回成功且不重复计入。

## 合并分片

`POST /api/upload/merge`，`Content-Type: application/json`。

```json
{
  "uploadId": "opaque-upload-id",
  "fileHash": "0123456789abcdef0123456789abcdef"
}
```

服务端确认所有分片齐全、按序合并并校验最终文件 Hash，然后保存 FastDFS 文件和数据库记录。成功返回 `201 Created` 与最终 `FileResponse`。未收齐分片返回 `409 INCOMPLETE_UPLOAD`；Hash 不匹配返回 `400 HASH_MISMATCH`。合并成功后，后续普通文件列表和下载接口应立即可见。

## 错误格式

沿用通用错误 DTO：`{ "code": string, "message": string, "fields": {} }`。至少约定：

- `400 INVALID_INPUT`：初始化参数或分片参数不合法。
- `401 UNAUTHORIZED`：Bearer Token 缺失或无效。
- `404 UPLOAD_NOT_FOUND`：上传任务不存在或不属于当前用户。
- `409 INCOMPLETE_UPLOAD`：仍有分片未上传。
- `413 MAX_UPLOAD_SIZE_EXCEEDED`：文件超过总大小限制。
- `503 STORAGE_UNAVAILABLE`：Redis/FastDFS 等依赖暂不可用。

分片失败时前端允许单片重试；浏览器中断后，用户重新选择相同文件，前端重新初始化并查询状态后续传缺失分片。未完成任务需由服务端设置过期清理策略；取消上传只中止当前客户端请求，不代表服务端已立即清除暂存分片。
